Let me think through this more carefully now, designing the actual Go service with the race condition, the harness, the tests, and all the checks.

The core scenario: A Go upload service with a buggy checkpoint writer. The race is:
1. No mutex on read-modify-write of checkpoint (lost progress)
2. No fsync of chunk data before checkpoint update (checkpoint claims durability that data doesn't have)
3. No fsync of checkpoint tmp before atomic rename (checkpoint can be zero-length after crash)

The fix: Add a mutex, fsync chunk before checkpoint, fsync tmp before rename, atomic write-tmp-fsync-rename sequence.

For the harness: It uses the debug hooks already in the source code to control goroutine scheduling and inject crashes at each step. The harness drives the upload, crashes, resumes, and checks. It's a Go program in tests/ compiled from /app source.
